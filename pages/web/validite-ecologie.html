Validité & écologie : pourquoi c’est important

Un site valide (W3C) et éco-conçu est plus fiable, plus accessible, plus rapide et consomme moins de ressources (batterie, CPU, réseau). Ci-dessous : méthodes, checklists et exemples pour intégrer ces pratiques dans tes projets ETUPEDIA.

Voir aussi : HTML • CSS • JavaScript

Valider son HTML & CSS (W3C)

HTML — Nu HTML Checker

  • Ouvre le validateur et colle l’URL ou le code source.
  • Corrige les erreurs : balises non fermées, attributs invalides, structure des titres, roles ARIA.
  • Répète jusqu’à 0 erreur. Les “warnings” sont souvent utiles à traiter aussi.
<img src="logo.png" alt="Logo ETUPEDIA">
<nav aria-label="Navigation principale">...</nav>

CSS — W3C CSS Validator

  • Valide tes feuilles : erreurs de syntaxe, propriétés inconnues, unités incohérentes.
  • Favorise des :root { --tokens } et évite !important inutiles.
:root { --brand:#275afe; }
.button { background: var(--brand); border-radius: 12px; }

Accessibilité & base SEO (rapide)

  • Hiérarchie des titres logique (un h1 par page, puis h2, h3…)
  • Contraste suffisant, focus visible, alternatives textuelles, labels reliés aux champs.
  • Métadonnées : <title>, meta description, liens internes, balise canonical.

Écoconception : principes & actions concrètes

Idée clé : moins de données, moins de complexité, plus de sobriété → meilleures perfs et moins d’énergie.

1) Réduire le poids des pages

  • Images : formats modernes (AVIF/WebP), dimensions adaptées, loading="lazy", decoding="async".
  • Vidéo : poster optimisé, pas d’autoplay, bitrate adapté, sous-titres.
  • Polices : self-host, font-display: swap, limiter les variantes.
  • CSS/JS : minifier, supprimer le code mort, charger en defer, splitter par page si besoin.
<img src="hero.avif" width="1200" height="630" alt="Bannière"
     loading="lazy" decoding="async">
<script src="/assets/js/page.js" defer></script>

2) Limiter le travail CPU & réseau

  • Éviter les timers et animations permanentes ; respecter prefers-reduced-motion.
  • Déclencher les requêtes au bon moment (intersections, interactions).
  • Mettre en cache (HTTP, immutable, Service Worker si PWA), compresser (Brotli), HTTP/2/3.
@media (prefers-reduced-motion: reduce) {
  * { animation:none; transition:none; }
}

3) UI sobre & accessible

  • Éviter les carrousels lourds, privilégier texte + image optimisée.
  • Boutons/liaisons clairs, focus visible, contrastes AA/AAA.
  • Dark mode : utile sur OLED, mais penser d’abord à la simplicité (moins d’assets, moins de JS).

Exemple : image responsive sobre

<picture>
  <source type="image/avif" srcset="/img/cover-800.avif 800w, /img/cover-1600.avif 1600w" sizes="(max-width:900px) 90vw, 800px">
  <source type="image/webp" srcset="/img/cover-800.webp 800w, /img/cover-1600.webp 1600w" sizes="(max-width:900px) 90vw, 800px">
  <img src="/img/cover-800.jpg" width="800" height="450" alt="Couverture" loading="lazy" decoding="async">
</picture>

Mesurer & suivre

  • Core Web Vitals (Lighthouse) : LCP, CLS, INP. Corriger les lenteurs réelles.
  • Eco-index / Website Carbon : estimation de l’empreinte (à prendre comme indicateurs, pas des absolus).
  • Budget de performance : se fixer des seuils (poids total, requêtes, JS exécutable).

Workflow recommandé

  1. Coder sémantique (HTML) + styles sobres (CSS) + interactions ciblées (JS).
  2. Valider (Nu HTML Checker, CSS Validator).
  3. Auditer (Lighthouse) + corriger perfs & accessibilité.
  4. Optimiser médias, minifier, activer cache/HTTP/2/3, COMP/Brotli.
  5. Suivre dans le temps (CI de lint/format/validate, budgets Lighthouse).
